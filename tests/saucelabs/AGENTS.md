# saucelabs

The `tests/unit-browser` pages, run in Sauce Labs browsers that the CI runners do not have: Safari on macOS and in the iOS simulator, Internet Explorer 10, and older versions of Chrome, Edge, Firefox, and the Android emulator. `platforms.mjs` lists them.

## Target environment

The runner uses the Node.js version supported by the repository's tooling. The WebDriver client next to it is plain HTTP, because it has to speak the JSON Wire protocol too, and the maintained clients have dropped that protocol.

## Rules

- The run opens the pages deployed to GitHub Pages over HTTP, never a local build: Firefox before 27 cannot negotiate the TLS versions served by the Pages CDN, so Pages must allow HTTP (disable Enforce HTTPS). `npm run test-saucelabs -- <URL of a branch directory> [commit]` tests what is deployed there. With a commit - the full SHA, as `commit.txt` holds it - the runner checks the marker before and after testing. A mismatch, missing marker, or network error produces a warning but does not fail passing browser pages: active development routinely redeploys the whole site and can replace or remove the marker. The Pages CDN can also cache older bundles after updating `commit.txt`, so the Pages build appends the commit as a query to the script URLs of the pages and pushes it to `window.bundleCommits` at the end of each bundle. That marker, not `commit.txt`, shows what the browser executed, so a page whose bundles carry another commit fails; bundles without the marker, deployed by an older workflow, produce only a warning
- The run is in the Pages workflow, not in `ci.yml`, and only for the branches of the main repository that the workflow builds pages for: the job has to run after the deploy, and the credentials (`SAUCE_USERNAME`, `SAUCE_ACCESS_KEY`; locally `SAUCE_REGION` can select a data center such as `eu-central-1`, default `us-west-1`) do not reach forks. `npm run test-saucelabs-matrix` runs the runner's local regression tests in a single `ci.yml` job, not in the OS and Node.js matrix, since the runner works only on the Pages workflow runner; it does not start live Sauce Labs sessions or run in the `npm test` composite. The job runs only when the deployment holds pages built from the triggering commit, and a newer push of the branch cancels it. The runner lists its open sessions in `SAUCE_SESSIONS_FILE`, and a step of the cancelled job closes them: GitHub Actions signals only the top process of a step, which npm does not pass on, so the runner cannot close them itself. The job does not fail the workflow (`continue-on-error`) while the failures it found on the old engines are open - read its log, not the workflow badge
- A new page in `tests/unit-browser` runs only once it is added to `pages` in `unit.mjs`, which lists the pages separately from the pages themselves. A listed page without `qunit-results.js`, or without the QUnit it attaches to, fails as `no results reporter`
- Another suite is an entry next to `unit.mjs` that passes its pages, platforms and results evaluation to `run` from `helpers.mjs`. Its pages publish a JSON-serializable object under the global the suite names and set `done: true` in it at the end - `qunit-results.js` sets it one second after the last `QUnit.done`, because QUnit 1 reports a global error after the run as one more test and calls `done` again; a page that never does is waited for up to the run timeout on every platform and then fails as not finished
- `platforms.mjs` selects older desktop engines and mobile browsers that CI lacks, and its `desktop` decides the WebDriver protocol of a desktop browser for both matrices. The latest desktop Chromium and Firefox, WebKit and IE11 run on the CI runners, so they do not need duplicate Sauce Labs sessions; the comment at the top of the file explains the version selection. To run one configuration per supported browser version, use `npm run test-saucelabs -- <URL of a branch directory> [commit] --all`. The script passes its arguments literally (`-- --`, as `scripts/zxi.mjs` describes), so `--all` arrives in `argv._`: the runner takes the URL and commit from the other arguments, and any other option, such as `--all=false`, or an argument after the commit is an error. The `--all` option fetches the live Sauce Labs platform catalog for `SAUCE_REGION` and includes desktop Chrome, Firefox, Safari, Edge, Internet Explorer, and Android Chrome and iOS Safari simulators. It selects one OS or simulator per browser version (one iOS session for an iPhone/iPad version), including beta and dev versions when listed. The choice must not depend on catalog order: for mobile entries, prefer a full emulator name over a missing one and break ties on all device and OS fields. Android emulator sessions require the catalog's full emulator name; the short `device` name is interpreted as a real device by Sauce Labs. It does not run every OS and device combination. The full run opens hundreds of sessions and is not used by CI
- Before the first session, the runner reads the plan's limit from `GET /rest/v1.2/users/<username>/concurrency` with the hub credentials and starts at most the smaller of the organization and team `allowed.vms` sessions in parallel; remaining platforms wait in the runner rather than in the Sauce Labs queue. The same response limits the pools within that total: `platforms.mjs` assigns a Mac session to `mac_vms` or, for macOS 14+ and the iOS 18+ simulator that Sauce Labs runs on Apple Silicon, to `mac_arm_vms`, and an ARM Android emulator to `android_arm_vms`; a worker skips a platform whose pool is full, and a platform whose pool the plan lacks (limit 0) fails without a session. A failed request or a zero total fails the run before any session. The limit is the plan's, not the free slots: runs of different branches can overlap and then share the slots through the Sauce Labs queue.
- A WebDriver error retries the whole platform in a new session. A page that does not finish within the 3-minute run timeout is retried the same way: a hung emulator and a test that never ends look alike, so only the last attempt reports it as not finished, with the current test. The session stops at such a page: a browser busy with it does not navigate, and the next page would read its results, so the report lists the remaining pages as not run. A failed assertion, a run without assertions, and a page without the reporter are results and never retried. A page that stops answering WebDriver altogether looks the same as a broken VM, so it is retried like one

# saucelabs

The `tests/unit-browser` pages, run in Sauce Labs browsers that the CI runners do not have: Safari on macOS and in the iOS simulator, Internet Explorer 10, and older versions of Chrome, Edge, Firefox, and the Android emulator. `platforms.mjs` lists them.

## Target environment

The runner uses the Node.js version supported by the repository's tooling. The WebDriver client next to it is plain HTTP, because it has to speak the JSON Wire protocol too, and the maintained clients have dropped that protocol.

## What is tested, and where

- `npm run test-saucelabs -- <URL of a branch directory> [commit]` tests the pages deployed to GitHub Pages, never a local build, and over HTTP: Firefox before 27 cannot negotiate the TLS versions served by the Pages CDN, so Pages must allow HTTP (disable Enforce HTTPS). `CONTRIBUTING.md` describes the command for contributors and changes together with it
- With a commit - the full SHA, as `commit.txt` holds it - the runner checks two markers. `commit.txt`, read before and after the run, only warns on a mismatch: active development redeploys the whole site and can replace or remove it. The Pages CDN can also serve older bundles after `commit.txt` has changed, so the Pages build appends the commit to the script URLs of the pages and pushes it to `window.bundleCommits` at the end of each bundle; that marker shows what a browser executed. A bundle of another commit stops the whole run as soon as a browser reports it, with or without the QUnit reporter; bundles without the marker, deployed by an older workflow, only warn
- A stopped run leaves no session open: no platform, page or retry starts, a session creation or a command already in flight finishes first, and every open session is then closed, the ones still testing marked failed
- The run is the `sauce-labs` job of the Pages workflow (`build-and-deploy-pages.yml`), not a part of `ci.yml` or of the `npm test` composite: it has to follow the deploy, and the credentials (`SAUCE_USERNAME`, `SAUCE_ACCESS_KEY`) do not reach forks. It runs only for the branches of the main repository that the workflow builds pages for, only when the deployment holds pages built from the triggering commit, and a failed run fails the workflow
- A newer push of the branch cancels the job. GitHub Actions signals only the top process of a step, its shell, which does not pass the signal on, so the runner cannot close its sessions itself and outlives the cancelled step: it lists the open sessions in `SAUCE_SESSIONS_FILE`, and a later step of the job first kills the runner, which would open a new session in place of each closed one, and then closes them. A session that was still being created is in no list; Sauce Labs ends it itself, as idle after 90 seconds or as never claimed. That step addresses the `us-west-1` hub, the default; locally `SAUCE_REGION` selects another data center, such as `eu-central-1`

## Matrices

- The manual matrix in `platforms.mjs` is what CI runs. The latest desktop Chromium, Firefox and WebKit and IE11 run on the CI runners (`tests/unit-karma`), so they get no Sauce Labs sessions. A version is in the matrix because a workaround of core-js executes in it - it is inside the window of an engine bug, the last version with the bug, or the first one the code trusts by its number - or because it stands next to a version where the compat data change for many modules at once; a version that falls into several windows is preferred. Before replacing or dropping one, find its windows: the engine version checks and comments in `packages/core-js`, the detections in `tests/compat/tests.js`, `CHANGELOG.md`, the versions in `packages/core-js-compat/src/data.mjs`
- `desktop` decides the WebDriver protocol and the Selenium version of a desktop browser for both matrices. Its boundaries are what Sauce Labs starts, not what the browsers support, and Sauce Labs moves them: a version whose session dies at creation on every attempt is tried in the other protocol and with another Selenium version before it is dropped
- `npm run test-saucelabs -- <URL of a branch directory> [commit] --all` runs one configuration per browser version that `fromCatalog` in `all-platforms.mjs` keeps from the live Sauce Labs catalog of `SAUCE_REGION`, beta and dev included: hundreds of sessions, not used by CI. The script passes its arguments literally (`-- --`, as `scripts/zxi.mjs` describes), so `--all` arrives in `argv._`; any other option, such as `--all=false`, and an argument after the commit are errors
- `fromCatalog` takes one OS per desktop version and one simulator per mobile one (an iPhone and an iPad of a version are one browser), preferring the OS and device of the manual matrix, and the choice must not depend on the order of the catalog. Its exclusions never drop a platform of the manual matrix. The catalog does not list the browser of an emulator or a simulator, so `repeated` - the versions whose engine a selected neighbour already has - is kept by hand from `navigator.userAgent` of their sessions
- Before the first session, the runner reads the plan's limits from `GET /rest/v1.2/users/<username>/concurrency` and starts at most the smaller of the organization and team `allowed.vms` sessions in parallel; the other platforms wait in the runner, since a wait in the Sauce Labs queue counts towards the session timeout. The request gets `ATTEMPTS` tries, a polling interval apart; a request that fails every time or a zero total fails the run before any session. A platform whose sessions also count towards a pool within that total - `mac_vms`, `mac_arm_vms`, `android_arm_vms` - names it in `pool`: a worker skips a platform whose pool is full, and a platform whose pool the plan lacks fails without a session. An iOS simulator counts towards the pool of its host Mac. A small pool runs its platforms one after another, so each platform added to it lengthens the run by its whole duration. The limits are the plan's, not the free slots: runs of different branches overlap and then share the slots through the Sauce Labs queue

## Runner

- A suite is an entry like `unit.mjs` that passes its pages, platforms and results evaluation to `run` from `helpers.mjs`. A page publishes a JSON-serializable object under the global the suite names and sets `done: true` in it at the end; a page that never does is waited for up to the run timeout on every platform and then fails as not finished. `qunit-results.js` sets it a second after the last `QUnit.done`: QUnit 1 reports a global error after the run as one more test and calls `done` again
- A new page in `tests/unit-browser` runs only once it is added to `pages` in `unit.mjs`. A listed page without `qunit-results.js`, or without the QUnit it attaches to, fails as `no results reporter`
- A platform gets up to `ATTEMPTS` sessions. A WebDriver error retries it in a new session, and so does a page that does not finish within `RUN_TIMEOUT`: a hung emulator and a test that never ends look alike, so only the last attempt reports the page as not finished, with the current test. The session stops at such a page - a browser busy with it does not navigate, and the next page would read its results - and the report lists the remaining pages as not run. A failed assertion, a run without assertions and a page without the reporter are results and are never retried
- Results of the previous page are not an error for `REPORTER_TIMEOUT` after a navigation: a slow simulator shows that page for a while
- A driver disturbs the page it is asked about, so a running page gets nothing but the poll, one per `POLL_INTERVAL` or per `pollInterval` of the suite, and the first poll goes an interval after the navigation, never earlier. Two cases are known, each described where it is handled: the driver of Firefox 48 - 50 cancels a page timer on every command (`runPage` in `helpers.mjs`), and Appium answers a command that waits for an iOS page over a second with an accessibility snapshot that stops the page, which the next polls then keep restarting (`ios` in `platforms.mjs`)

## Tests of the runner

- `npm run test-saucelabs-runner` runs the files of `tests/` through its `index.mjs` without a live session; each is named after what it tests, and a new one is imported there. It is a single `ci.yml` job, outside the OS and Node.js matrix and the `npm test` composite: the runner works only on the Pages workflow runner
- The tests replace `fetch`, and the abort scenarios keep their mocks inside child processes: the parent kills a stalled child and waits for its exit before removing its temporary files, since restoring the real `fetch` while `run` is still alive would send test requests to Sauce Labs
- A test passes its own `pollInterval`: with the default one, every fake page takes five seconds

## Looking into a session

- The report links every session it tells about: the last one of a platform and the one of each retried attempt. All the sessions of a run are in the build `<suite name> <branch directory>`
- A finished session keeps its logs: `GET https://api.<region>.saucelabs.com/rest/v1/<username>/jobs/<id>/assets/<file>` with the hub credentials returns `log.json` - every command with its duration and answer, `selenium-server.log` - the log of the driver, Appium for a simulator or an emulator, and the system log of an iOS simulator, `ios-syslog.log`, or of an Android emulator, `logcat.log`. Read them before starting sessions to reproduce a hang: polls that take seconds mean a busy page, instant polls with the same current test - a page that waits for a timer or a promise. A session stopped through the REST API keeps no logs

# saucelabs

The `tests/unit-browser` pages, run in Sauce Labs browsers that the CI runners do not have: real Safari, iOS and older Chromium and Gecko.

## Target environment

The runner is on the tier of `tests/AGENTS.md`. The WebDriver client next to it is plain HTTP, because it has to speak the JSON Wire protocol too, and the maintained clients have dropped that protocol. What runs in the browsers is the published pages and `tests/unit-browser/qunit-results.js`, which they load. That file is ES5, because it runs in every browser of the matrix.

## Rules

- The run opens the pages deployed to GitHub Pages, never a local build. `npm run test-saucelabs -- <URL of a branch directory> [commit]` tests what is deployed there. With a commit - the full SHA, as `commit.txt` holds it - the runner first waits for the `commit.txt` that the Pages workflow writes to show that commit, and fails if a redeploy changes it during the run. That proves the deploy, not the bundles a browser gets: GitHub Pages caches its responses, and the runner does not wait that out, so a run in the first minutes after a deploy can test the previous commit on an edge that still serves it. The marker comes only from a version of the workflow that has the step writing it, and every deploy rebuilds the pages of all branches: a deploy started from a branch whose workflow lacks that step removes `commit.txt` everywhere, and the run reports `HTTP 404` instead of the commit. Without a commit, nothing ties the result to your tree
- The run is in the Pages workflow, not in `ci.yml`, and only for the branches of the main repository that the workflow builds pages for: the job has to run after the deploy, and the credentials (`SAUCE_USERNAME`, `SAUCE_ACCESS_KEY`, optional `SAUCE_REGION`, a data center such as `eu-central-1`, `us-west-1` by default) do not reach forks. `npm test` does not include it, and the job does not fail the workflow (`continue-on-error`) while the failures it found on the old engines are open - read its log, not the workflow badge
- A new page in `tests/unit-browser` runs only once it is added to `pages` in `unit.mjs`, which lists the pages separately from the pages themselves. A listed page without `qunit-results.js`, or without the QUnit it attaches to, fails as `no results reporter`
- Another suite is an entry next to `unit.mjs` that passes its pages, platforms and results evaluation to `run` from `helpers.mjs`. Its pages publish a JSON-serializable object under the global the suite names and set `done: true` in it at the end; a page that never does is waited for up to the run timeout on every platform and then fails as not finished
- `platforms.mjs` holds only what CI lacks. The latest Chromium, Firefox and WebKit and IE11 run on the CI runners, so they never go here; how the versions are picked is in the comment at the top of the file. To run one configuration per supported browser version, use `npm run test-saucelabs -- <URL of a branch directory> [commit] --all`. The `--all` option fetches the live Sauce Labs platform catalog for `SAUCE_REGION` and includes desktop Chrome, Firefox, Safari, Edge, Internet Explorer, and Android Chrome and iOS Safari simulators. It selects one OS or simulator per browser version, including beta and dev versions when listed. Android emulator sessions require the catalog's full emulator name; the short `device` name is interpreted as a real device by Sauce Labs. It does not run every OS and device combination. The full run can consume hundreds of paid sessions and is not used by CI
- The account dashboard showed a total concurrency limit of 10 sessions, Mac/iOS (x86) concurrency of 15 and real device concurrency of 0 on October 30, 2026 (see `CONTRIBUTING.md`). The default matrix is sized to the total limit. The full matrix starts at most ten sessions in parallel; other platforms wait in the runner rather than in the Sauce Labs queue. Recheck the account dashboard if the plan changes
- A WebDriver error retries the whole platform in a new session. A failed assertion, a run that does not finish or has no assertions, and a page without the reporter are results and never retried. A page that stops answering WebDriver altogether looks the same as a broken VM, so it is retried like one

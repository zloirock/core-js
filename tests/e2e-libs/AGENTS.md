# e2e-libs

Real third-party libraries taken to the polyfill floor and executed there: each is bundled, down-compiled to ES5 by Babel, polyfilled by one of the two providers this repo ships, then run - in a node pre-flight and in the browsers, real IE11 among them. `tests/transpiler-integration` proves the plugins survive a real bundler and `tests/e2e-usage-pure` proves a syntactic form is served; the unit suites reach IE11 too, but on core-js's own tests. What only this suite does is put all three together - third-party code, the providers, and the engine the polyfills exist for.

## Target environment

Node under `zx`, started through `npm run zxi` - the repo-wide tooling tier, stated in `scripts/AGENTS.md`. The suite declares no floor of its own, and CI exercises it on one version only, the node 26 its job pins. The exception is what lands in a page verbatim: the programs under `harness/` and the HTML `page.mjs` renders are never transformed, so they are hand-written ES5 - and they are real files, which is what puts them under eslint at `ecmaVersion: 5` rather than under a parse at run time.

`npm run test-e2e-libs` chains the three runners - `test-e2e-libs-check-exercise`, `test-e2e-libs-runtime`, then `test-e2e-libs-karma-run` - and is part of `npm test`; `OVERWRITE=1` in front of the runtime one rewrites the snapshot baselines. Each narrows on a positional filter, as in `npm run test-e2e-libs-runtime three`. There is no fourth runner: everything the suite measures, it measures on the build it is already making.

The floor is the one the root `AGENTS.md` states - `IE 11, Chrome>=38, Safari>=7.1, FF>=15`, declared ONCE in `cells.mjs` and read by the provider and by preset-env alike, spelled as `scripts/bundle-tests` spells it for the e2e-usage-pure bundles. IE11 alone would be narrower by what only old Safari, Firefox and Chrome lack - `Array.prototype.reduce`, `indexOf`, `unshift`, `reverse`, `parseInt`, `Date.prototype.toJSON`, `Object.setPrototypeOf` among them.

This directory's `package.json` pins the libraries, `core-js` to the workspace, and the Babel side of the down-compile - `@babel/core`, `@babel/preset-env` and `@rollup/plugin-babel`, which configures the two rather than reimplementing them. Rollup and its two resolvers are pinned here and driven directly - one bundler, called in one place, so the ten-bundler install of `tests/transpiler-integration` buys nothing. Two modules do come from there, and neither pulls anything in, so they cross the directory boundary without an install: `warning-policy.mjs`, because how an unresolved injection and unplugin's own `PLUGIN_WARNING` are escalated is the one question both bundler suites have to answer identically, and `matrix.mjs`, the axes `cells.mjs` reads. The browser stack is not here either. The browser leg runs out of `tests/karma` instead, over its config, its Playwright launcher and its install, and installs itself. The ES5 parse gate is `scripts/assert-es5.mjs`, shared with the e2e bundles of `scripts/bundle-tests`.

No minifier is pinned here either. The wire size of every cell - minified, then gzipped - is reported by the gating tier itself, through the settings `@core-js/builder` publishes as `@core-js/builder/config.js`, the ones core-js itself ships under; `@swc/core` behind them resolves from the root tree as that package's dependency. Measured before it was moved here, because the alternative was a second pass: minifying and gzipping the whole matrix costs a fraction of what building it does, and it shards with the builds. What that buys is not the saved script - it is that the published number describes the bundle that was gated, pre-flighted and handed to the browsers, rather than a second build of the same configuration.

Rollup rather than rolldown, and that was measured rather than assumed: rolldown's own generated wrapper never passes through the plugin chain, so it stays ES2015 whatever transpiler sits in front of it, and its built-in oxc rejects `target: 'es5'` and silently ignores `'ie11'`. `@core-js/builder` gets around exactly that by running SWC over the finished bundle; this suite cannot reach its floor that way, because what it measures is a provider running per module - it runs SWC over a finished bundle only to weigh one. The polyfill stack it does not pin at all: `@core-js/pure`, `@core-js/unplugin` and `@core-js/babel-plugin` resolve through the root `node_modules`, where the workspace glob links them, and `oxc-parser` - unplugin's parser, and the one package whose per-platform native bindings can differ between two runners at an identical version - is hoisted there as unplugin's own dependency. So for everything those four decide, "the suite bundles the workspace copy" rests on node walking up rather than on a pin, and the two lockfiles a run digests - this directory's and the root - are what answer for the versions behind all of them. Same in `tests/transpiler-integration`. Only one bundler is used here, and the bundler axis belongs to that suite. The browser leg is `tests/karma/e2e-libs.mjs` and runs the same browsers as the unit legs: Chromium, Firefox and WebKit through Playwright, plus IE11 wherever `tests/karma/karma.conf.js` expects one - on CI, or on a machine that has the browser. That resolution is `tests/karma/internet-explorer.js`: `IE_BIN`, then the standard location under each flavor of the program files directory. `PATH` is not consulted and a stock windows install keeps IE out of it, so `IE_BIN` is what names a browser installed anywhere else. IE11 is the one engine here no other tier reaches, and it is why the `e2e-libs` job runs on windows; on a CI runner without IE11 the config would start it and fail, so no other job may run this suite. A green `npm test` is therefore not a green CI here.

## Layout

Five groups, and the split is by the question a module answers rather than by the runner that asks it. Nothing in the first group loads a bundler: a runner that only wants to know what a cell is called, or to print one line about a failure, must not pull rollup, Babel and unplugin in to find out.

Three mechanisms here are hand-written while a canon sits next door, and the reason differs for each. `check-exercise.mjs` counts by hand rather than through `createChecker` from `tests/polyfill-provider/harness.mjs`, which 24 files do use: that one counts INCREMENTS behind a closure only its `finish()` reads, while both tiers here count by IDENTITY - a target that fails twice is one broken exercise - and a sharded tier has to hand its counters to a parent. Adopting it would also drop the per-check `ok` lines, which are the raw tier's whole output. Every module that touches the filesystem imports `node:fs` rather than the fs-extra `zx` makes ambient, and that is not style: it is what lets all eight of them load under a bare `node`, which `preflight-child.mjs` runs on and every direct probe of a module depends on. And `ts-sources.mjs` RESOLVES to `src/**/*.ts` where an off-the-shelf TypeScript plugin would COMPILE, needing a pin of its own and a second opinion about the syntax - here Babel strips the types in the pass that is already running.

**The matrix and the identity of a cell**

- `cells.mjs` - the axes (from `tests/transpiler-integration/matrix.mjs`), the compile target every cell shares (`SUPPORTED_ENGINES`, declared ONCE and read by the provider and preset-env alike - a constant, not a fifth axis: nothing varies over it), and `cell()`, which computes a cell's identity: its label, its path segments, its snapshot file, its group, and whether it is the reference. Everything that names a cell reads a field from here. `groupByLibraryAndMethod()` is what a shard slices, and it takes a whole group rather than a cell, because every unplugin cell is diffed against the babel-plugin cell of its own group
- `libraries.mjs` - the registry: one entry per library and its exercise. `librariesMatching` throws on a filter matching nothing, so a typo cannot produce a green empty report
- `paths.mjs` - where this suite keeps things, and the posix normalisation several of its modules need
- `diagnostics.mjs` - what the suite says when something fails: the reason extractor and the failing-check line. Formatters only, dependency-free, and it may not touch a zx global ANYWHERE - `preflight-child.mjs` imports it and runs under a bare `node`. That is the whole split from `output.mjs`, which prints. The page's own copy of the same policy is `harness/shared.js`
- `output.mjs` - every line a run says ABOUT ITSELF: the header, a cell's verdict, the tally, and each phrase more than one tier repeats. The `ok`/`FAIL` prefix a matrix-wide log is read by is a contract, and it had already drifted while each runner owned its own copy - `SCOPED RUN: ... not a full verification` stood verbatim in all three, and the same `pre` phase of the same cell was a "gap" in one and a "failure" in another. A line added to a runner instead of here re-forks it, and nothing says so. The verdict is NOT here: nothing in this module sets `process.exitCode` or counts a failure. Neither is the detail a module prints about its own subject - the `+`/`-` lines of a snapshot diff stay in `snapshots.mjs`. zx-bound, which is the whole split from `diagnostics.mjs` beside it, so `preflight-child.mjs` may never import it

**Building one**

- `bundle.mjs` - one story in one file, behind one function: `buildCell`. The entry rollup is given, the chain that turns a library into a polyfilled ES5 bundle, what that build recorded on the way through, and the four gates it has to pass - no externals, an ES5 parse, a real core-js payload, a non-empty injection set. The gates are applied HERE, on the way out of the build, so no call site can forget one and none repeats one; the entry is a VIRTUAL module whose id is a path under this directory, which is what lets `nodeResolve` answer a bare `core-js` or `rxjs` from it, and there is no temp file, no pid-named scaffold and no sweep for the runs that were killed before removing theirs. The recorder reads specifier TEXT, at two points of the chain, and where a plugin sits against it is load-bearing: `commonjs()` rewrites every `require` in a CommonJS module into a resolved id the scan cannot read, so a plugin that rewrites specifiers ahead of the unordered pass takes its modules out of every baseline while the bundle and every gate stay green. What holds it there is the corpus: ml-matrix's implementation is one CommonJS file, `matrix.js`, behind an ESM wrapper, so every polyfill its checks drive is injected into it, and the echarts baselines carry a second case through fast-xml-parser 4.x and `strnum`, the packages its exercise reads the SVG with
- `babel.mjs` - the down-compile: which toolchain, which configuration, and which modules it may touch. `@rollup/plugin-babel` does the wiring; this configures it. `babelHelpers: 'inline'` is not a detail - `bundled` moves Babel's helpers into a module the BUNDLER mints, which no provider transforms, so the polyfills the helpers need leave the bundle while every gate here stays green
- `ts-sources.mjs` - the plugin that serves a few packages from their own `src/**/*.ts`, which is what gives the `phase` axis something to be about. MUST sit before `nodeResolve`
- Rollup is called here, directly and in one place - `tests/transpiler-integration/bundlers.mjs` is the bundler AXIS, ten adapters and the install behind them, and that suite's alone

**Running one**

- `preflight.mjs` and `preflight-child.mjs` - the full-env pre-flight: a process per bundle, because `mode: 'full'` patches globals permanently. The bundle travels on STDIN and the child executes it with `runInThisContext`, so there is no temp file on this path either
- `deadline.mjs` - the bound on an in-process wait. It pulls nothing in, which is what lets the raw tier take it: `check-exercise.mjs` must not load a bundler to time a call. Its header states why the repo's other one, `timeLimitedPromise`, is not this
- `stripped-realm.mjs` - the `usage-pure` oracle: the built bundle re-run in a `node:vm` realm with the leaf builtins deleted, over `tests/transpiler-differential/strip-manifest.mjs` - the same manifest and applier `tests/unit-node/stripped-realm.mjs` runs over the e2e-usage-pure bundles. It returns a verdict on the cell, held to the pre-flight's label SEQUENCE before any check is asked whether it passed
- `harness/` - the two page programs and `shared.js`, the guards and the reason formatter they answer alike - a guard written twice drifts once - as hand-written ES5 FILES rather than generated text, which is what puts them under eslint: `ecmaVersion: 5` catches an arrow that would be a SyntaxError in IE11, and the es-x rules catch a modern built-in - `Map`, `Set` and `WeakMap` among them, which the shared ES2015 set omits and this block names itself. `no-undef` answers only for a name NOTHING declares: flat config merges `languageOptions.globals` across every matching block, so an earlier one goes on declaring the modern globals whatever this block lists. Nothing at run time asks any of that any more. Two rules bind both programs. Nothing in them may call a method the bundle can REPLACE - a verdict computed with `Array.prototype.filter` counts failures using the code under test, and a substituted one returning `[]` reads as "nothing failed"; no exceptions, not even `join`, and the one unavoidable call is `then`, whose rejection handler goes to that same `then` rather than a later `.catch`. And the two are one instrument, carrying the same guards: the banner is what CI publishes when the job fails, which is exactly when someone opens it, so it may not be the weaker of the two
- `exercises/<lib>.mjs` - one deterministic exercise per library, exporting `run()` -> `{ checks }`; its header states what it drives and what it deliberately avoids. `exercises/checks.mjs` is the comparison they share, bundled and transpiled with them like any other module in the graph

**Recording it**

- `snapshots.mjs` - comparing a baseline, authoring one under `OVERWRITE`, and finding the ones no cell produces any more
- `manifest.mjs` - the lifecycle of `artifacts/manifest.json`: clear the directory before the first cell, write what the run built. The browser leg reads it through this module rather than parsing it a second way, and writes each cell's browser verdict back the same way
- `input.mjs` - what a run was fed, derived from the LOCKFILES rather than probed for in `node_modules`. A lock answers for a package whose `exports` map does not list its `package.json` and so cannot be asked directly
- `page.mjs` - the artifact page of a cell and the per-cell data both page programs read. The browser leg loads the files; the page inlines them, so the page and its `bundle.js` are the whole upload

**The runners**

- `runtime.mjs` - the gating tier, and the only place a cell is built. `check-exercise.mjs` - the exercises run raw, which separates a broken fixture from a broken toolchain, and run TWICE: determinism is asserted here, or a wobbling fixture reaches the gating tier and reddens a cell every other run, where it reads as a flaky toolchain. The bound on that in-process wait is `withDeadline` from `deadline.mjs` beside it; a child process gets zx's own `timeout` instead
- `snapshots/` is committed; `artifacts/` is generated and gitignored

## The matrix

`runtime.mjs` builds every (library x method x provider x phase) cell **once** and hands that build to every consumer - gates, snapshot, pre-flight, and the artifact page the browser leg then runs. Preserve that: the set that is snapshotted, the bytes that are measured and the bundle the browsers run are then the same build by construction.

The providers are not symmetrical and the snapshots mirror it. `@core-js/babel-plugin` runs inside the Babel pass and has no phase, so its set is the **reference**, stored whole; each `@core-js/unplugin` phase is stored as a **delta** from it, and an empty delta is written rather than omitted so that "agrees" is a recorded state. `entry-global` is snapshotted for neither - it never reads the library - and its cells assert that the providers agree on the expansion instead.

Gating: the ES5 parse, the core-js payload, no externals, a non-empty injection set, the snapshots, the forked pre-flight, the stripped realm on every `usage-pure` cell, and Karma on every cell except unplugin's `pre` - a per-library diagnostic that is red on some by design, and the whole of the not-gating list besides the numbers a cell reports - `buildMs`, `rawKb`, `minKb` and `gzKb`. A minifier that dies takes its own line and leaves the cell's verdict alone, for exactly that reason. Note what the exception is stated against: babel-plugin's cells carry no phase, so they gate like any other.

A green cell proves the exercise executes, not that every site was detected: a global polyfill patches the prototype once, so one detected use masks a missed sibling. Per-site detection for the global methods is the job of `tests/unplugin/unit.mjs`.

`usage-pure` has no such masking, and the leg that sees it is `stripped-realm.mjs`: the full-env pre-flight and every browser but IE11 answer a missed rewrite with the native, so of the four browsers the leg starts only IE11 sees it - and IE11 joins on CI or on a machine that has it. In a realm with those builtins deleted a missed rewrite is a raw read that throws - which is what unplugin's `pre` phase does on three.js, from a `Array.from` inside a Babel helper emitted after unplugin had already looked. `pre` stays a diagnostic there for the same reason it is one under Karma. The same gap is what the `pre` delta of every library whose classes Babel lowers records as a missing `object/set-prototype-of` - `es.` in the global spelling, `@core-js/pure/full/` in the pure one: Babel's `_inherits` reaches for it, and at `pre` that helper does not exist yet. It is only visible at all because the floor is wider than IE11, which has `setPrototypeOf` and needs no polyfill for it.

## Rules

- The library's own implementation has to reach for what the target lacks; an exercise reaching for it on the library's behalf tests Babel's helpers instead. Judge a check by which frame makes the call, not by which names appear in the file - `from(new Set(...))` counts, `[...new Set(...)]` does not
- A check must REDDEN under an identity implementation of the mechanism it names. Asserting a property the input already had, or one the operation cannot change, leaves the cell green while the thing it exists to observe does nothing at all - the same count back from a modifier that split nothing, the bounding box of a geometry whose rounding it never applied, an ordering operator whose output is then collected order-blind. The test is mechanical: replace the addon, operator or serializer with one that hands its input straight back, and rerun. Over a whole exercise it is one module - `export * from '<lib>'` plus one overridden name - imported in the exercise's place, which needs no edit inside `node_modules`; a name whose neutralised form reddens nothing is a check that describes its input. A check that survives that is describing the input, not the library
- Checks assert version-robust invariants, never magic totals, or a dependency bump reddens the suite for no reason
- A collision between a library member and a core-js instance method is deliberate coverage: `usage-pure` rewrites those call sites and the helper has to hand back the library's member, which only real IE11 catches
- `usage-pure` cannot serve typed-array prototype methods or statics at all, and IE11 has none of them either, so an exercise must not route a typed array through one. Indexing is fine - but what disqualifies a call is what it does INSIDE, not what it returns, and no local gate can see the difference: node and the stripped realm both have the natives, so a routed typed array is green everywhere until the browser leg. The stripped realm is where that is settled, and extending it is how a new case joins: the manifest it strips is `tests/transpiler-differential/strip-manifest.mjs`, which is deliberately conservative - leaf methods and the constructors no IE11 has, never the primitives core-js itself runs on
- `usage-pure` cannot reach a built-in the code gets from the ENGINE rather than from a name the provider can rewrite, and IE11 is where that shows. Two shapes, both found on es-toolkit: type detection through `Object.prototype.toString`, which the global flavor patches and the pure one may not - so a pure `Map` answers `[object Object]` there and every lodash-shaped `getTag` reads it as a plain object; and a constructor taken off an instance's prototype, which is the engine's own - IE11's `Error` keeps JScript's `Error(number, description)`, so `new Error(message, { cause })` lands the options bag in the message. Neither is a defect the polyfills can answer, and no tier the suite runs sees either: node and the local browsers have both built-ins, and the stripped realm keeps `Symbol` on purpose. A `node:vm` realm with `Symbol` deleted does reproduce the tag half, which is how that one was pinned; the `Error` half is IE11's own spelling, and only the CI leg has it. So an exercise must not assert through them; what it may still do is DRIVE them, since the entries stay injected
- A new library needs a reason on an axis. Topology is one, and it pulls on two costs at once: the plugin's own analysis scales with the size of a single module, which `tests/transpiler-perf` gates on a corpus much like this one, while the build around it scales with how many modules the injection adds for the bundler to resolve, parse and render - which nothing gates anywhere, and which only a real graph shows at all. Keep the small-modules, mid-sized-graph and monolith profiles represented. The phase axis is the second, and it needs TypeScript sources - `isolatedModules`-clean and listed in `TS_SOURCE_PACKAGES`. SURFACE is the third: polyfills the library's own frames reach that no library in the corpus does, measured against the union of the reference baselines - and weighed in `usage-pure` above all, where one detected use masks no missed sibling. Locally that holds only for a built-in the stripped realm deletes: one it keeps answers a sibling site the rewrite missed with the native, a baseline cannot tell one rewritten site from two, and IE11 on CI is then the only leg that sees it. Widening the strip is not this suite's to do alone - the manifest is shared with the differential and the unit legs - and neither a constant nor a well-known symbol can join it at all: `Number.EPSILON`, `MAX_SAFE_INTEGER` and `Symbol.replace` alike are non-configurable, so a realm cannot take them away. What answers for one of those locally is a scan of the built pure cell for a raw read outside comments, or a realm with the whole `Symbol` gone, which is the shape IE11 actually has. SYNTAX is the fourth: the provider reads code twice, and `detect-syntax.js` is the second table - one entry set per FORM, owed to whatever the DOWNGRADE of that form calls. Most of those sets are invisible in a baseline, because a library spelling a spread or a `for-of` also names `Array.from` and `Symbol.iterator` somewhere itself, and usage detection injects the same entries; a form earns a library its place only where the library never names the built-ins its lowering reaches. The named capture group is one such - `_wrapRegExp` re-dispatches `Symbol.replace` through a `WeakMap`, which is why colorjs.io carries `es.symbol.replace` - and it has to be a LITERAL: a pattern built with `new RegExp` at run time is nothing Babel can lower, so the flags reach the engine, and there the pure version has no RegExp of its own to answer with (es-toolkit and chrono-node build named groups that way; remeda's literal carries a sticky flag, which survives the lowering and dies on IE11 in `usage-pure` alone). Two forms cannot be reached here at all: a dynamic `import()` leaves the UMD bundle spelled as itself and the ES5 gate rejects it, and decorators are compiled away before a package is published. A module that is injected but never EXECUTED adds nothing, so the exercise has to drive the path that calls it. Only headless computational libraries qualify at all; core-js cannot make DOM or stream code run on IE11
- A library that reaches IE11 through this suite must survive IE11's RegExp, and that is checked by RUNNING the built cell, not by reading it. No local tier sees the class: the pre-flight and the stripped realm run on node's RegExp, the local browsers have every flag, and the ES5 gate validates regex LITERALS only - a `new RegExp(source, flags)` call is a string to it. The flag also travels: fast-xml-parser 5.x reaches `new RegExp(..., 'u')` through a variable, inside a transitive dependency, at module load. So a candidate is screened by executing its cell in a realm whose RegExp refuses what IE11 refuses - the `u`, `s` and `y` flags, lookbehind, named groups, `\p{}` - installed BEFORE the bundle, so core-js wraps it the way it would on the real engine and emulates `s`, `y` and named groups while `u`, lookbehind and `\p{}` still throw. Run it in both a `usage-global` and a `usage-pure` cell: only the global flavor installs that wrapper, so a library building named groups at run time survives the one and dies in the other
- The same realm carries IE11's `DOMException`, which is an interface OBJECT rather than a constructor. No local tier answers that read as IE11 does - node hands out a constructible one and the vm realms have none - so a library guarding on `typeof DOMException !== 'undefined'` either extends node's or takes its `Error` fallback, and only the real engine has the third answer, where extending or constructing that object fails - es-toolkit's `TimeoutError` and `AbortError` extend it while their module bodies run. The polyfill is no rescue when the library reaches the global through an alias imported from another module: both providers analyse one module at a time, so that read injects nothing, and a polyfill injected for some other reason may run after it. Install the shape before the bundle, beside the RegExp, and run every cell
- Isolation is a requirement: `mode: 'full'` patches globals permanently, so the pre-flight forks a child per bundle and Karma loads one bundle per page. Co-loading lets one cell's injection mask another cell's miss
- Never regenerate a snapshot blindly - read the diff, then rerun with `OVERWRITE=1`. Deltas are measured FROM the reference, so a movement both providers share lands in the reference alone and leaves the delta files untouched; a delta that does change is the two of them disagreeing
- Timings are reported, never asserted, and never quoted in prose or in a comment - they move with the machine and go stale where nothing checks them. Sizes are reported too, and the rule holds for them: `rawKb`, `minKb` and `gzKb` are in the manifest and in the run's output, and nothing compares them against anything. A COUNT taken off a build is the one number prose may carry, because a library entry has to justify itself on an axis and "the widest graph here" is unverifiable without one - but it must name the build it came from, or it is a number from some other build: the module count of a cell built through its OWN entry points is not the count of the whole package, and the two differ by more than a factor of two here
- What the suite does not measure on the build it already has, it does not measure. The library's own weight before any transform is the one number that needs a build of its own - no provider, no down-compile - and it is taken by hand on the day it is asked for, not by a second runner kept warm for it
- The runtime tier shards itself over processes, through `runShards` in `tests/babel-plugin/fixture-shards.mjs` - the protocol both fixture runners use. The unit a shard takes is the (library x method) GROUP, never a cell: every unplugin cell is diffed against the babel-plugin cell of its own group, and a slice that split one would leave a phase with no reference. A shard builds and snapshots; the parent alone wipes `artifacts/` and writes the manifest. The rows travel back on the same marker as the counters: `runShards` adds numbers up and concatenates arrays in shard order, so a list needs no side channel of its own. `E2E_LIBS_SHARDS=1` runs it in one process, and the manifest it writes has to be row-for-row the one a sharded run writes - the layout is recorded in `sharded` and may not reach anything else. The work is CPU-bound, so the win is a fraction, not a multiple
- A run's manifest describes THAT RUN. A filtered one clears `artifacts/` like any other and lists the cells it was asked for, because those are the only pages on disk when it finishes. Splitting a full matrix across two invocations is deliberately NOT supported: it bought nothing and cost a merge, an input comparison to guard the merge, a second read of the file right before the write to catch a sibling that finished mid-run, and a rule that a filtered run may clear only its own libraries. Two runs at once in one checkout now race, and the loser's pages go - so do not start two
